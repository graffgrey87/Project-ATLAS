# Передача работы между агентами и экономия лимитов

Контекст переносится через файлы проекта, а не через историю чата.

## 1. Когда передавать
- При ~70-80% контекста или заранее, если задача большая.
- Не ждите, пока лимит кончится: после этого агент уже не сможет обновить файлы.

## 2. Чек-лист передачи (выполняет текущий агент)
1. Обновить раздел «Текущий фокус» в `PROJECT_MEMORY.md`: задача, статус, блокер, следующий шаг.
2. Записать журнал `sessions/YYYY-MM-DD-тема.md`: цель, что сделано, что осталось, решения, номер последнего коммита.
3. Сохранить в журнал сырые данные, которых нет в репозитории (текст ошибок, строки `ERROR:` из логов CI).
4. Новые решения оформить в `docs/adr/` и добавить строку в таблицу решений.
5. Выполнить `git add -A`, `git commit`, `git push`.
6. Проверить, что `PROJECT_MEMORY.md` не длиннее 300 строк.

### Готовое сообщение текущему агенту
```
Подготовь передачу работы: выполни чек-лист из docs/handoff.md
(PROJECT_MEMORY.md, журнал сессии, ADR при необходимости, commit и push).
В конце выведи итог: что сделано, блокер, следующий шаг и номер коммита.
```

## 3. Первое сообщение новому агенту
```
Прочитай PROJECT_MEMORY.md и последний файл в sessions/.
Кратко перескажи: текущий фокус, блокер, следующий шаг.
Дождись моего подтверждения и только потом продолжай.
Не читай весь репозиторий: используй точечный поиск.
```
Если агент пересказал блокер неверно, поправьте его до начала работы.

## 4. Как не тратить лимиты впустую
- Один диалог на одну задачу. Новая тема: новое окно и передача по чек-листу.
- Не вставляйте в чат длинные логи целиком. Нужны только строки с `ERROR:` и 5-10 строк вокруг.
- Не просите «прочитай весь проект». Указывайте конкретные файлы через `@файл`.
- Сначала просите план, потом реализацию по одному шагу (так и построен проект).
- После каждого шага: коммит и обновление фокуса в `PROJECT_MEMORY.md`.
- Проверяйте результат фактом (статус сборки, вывод команды), а не словами агента.
- Дорогие модели оставляйте для архитектуры и сложной отладки, мелкие правки делайте на лёгкой модели.
- Не повторяйте просьбу много раз подряд: лучше уточнить задачу одним сообщением.

## 5. Проверка перед закрытием сессии
- [ ] `git status` чистый, `git push` выполнен
- [ ] «Текущий фокус» отражает реальное состояние
- [ ] Журнал сессии создан
- [ ] Блокер записан вместе с текстом ошибки
